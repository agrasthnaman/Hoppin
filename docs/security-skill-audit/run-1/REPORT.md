## 2. Security posture

Hoppin's database layer is well built for its core promise. Row-level security covers every table, every privileged function checks its caller, and private plans never leak to other members through the change log, digests, or notifications. No critical or high-severity issue was found, and no committed secret was found in source or git history. The 12 confirmed findings (6 medium, 6 low) cluster in four places where that core discipline was not carried through:

1. **File references are not bound to their trip.** `documents.storage_path` is free text, and both the storage read rule and the client-side delete flows trust it. As a result, anyone who learns a file path can read a private file from another trip, including former members and users who were never members, and a planted row can make an organizer delete another trip's file. Binding the path to `<trip_id>/<owner_id>/` in the insert policy, making it immutable, and adding a trip-folder check to the storage read rule closes this.
2. **Sessions can be swapped without consent.** The Supabase client accepts a session from any URL fragment, and the invite page joins a signed-in visitor to a trip on load. One line in `apps/web/src/lib/supabase.ts` (`flowType: "pkce", detectSessionInUrl: false`) and an explicit "Request to join" button close the confirmed paths.
3. **Shared background work trusts member data.** One unvalidated time zone, or about 50 failing trips, stops digest notifications for every tenant. Out-of-range expense values also break settle-up for a whole trip. The fix is validation in the database plus a digest queue that quarantines failing trips and shares capacity fairly.
4. **Lifecycle cleanup is incomplete.** Account deletion leaves files and sign-up queue rows behind. Organizers can edit any `members` column directly, bypassing the RPC guards. The anonymous sign-up queue has no requester bound.

Eight further leads depend on facts outside the repository, so each needs an owner check. They are: hosted Supabase Auth behaviour and settings, Storage content-type handling, Cloudflare headers, and browser rendering.

## 4. Confirmed finding details

### 4.1 A crafted link with tokens in the URL silently replaces a signed-in user's session on any route (session fixation / login CSRF)

- **Severity:** medium (likelihood medium: The victim only has to open one crafted link to a Hoppin route. The attacker needs only their own reusable token pair. The app shows no prompt or confirmation. Impact medium: The victim's browser silently switches to an attacker-controlled identity, and sensitive data the victim then adds lands in an account the attacker can read. The victim's own account and existing data are not directly compromised.)
- **Confidence:** high — Every trace line was checked against the installed source. The behavior was independently reproduced with the installed supabase-js/auth-js 2.119.0 using the app's exact createClient call, and the proposed fix was shown to block it. Server-side, GoTrue only has to accept the attacker's own valid token for GET /user, which is normal behavior.
- **Fingerprint:** `apps/web/src/lib/supabase.ts:createSupabaseClient:implicit-detectSessionInUrl-replaces-existing-session`
- **Source:** `node_modules/@supabase/auth-js/dist/module/lib/helpers.js:66` → `apps/web/src/lib/supabase.ts:17` → `node_modules/@supabase/auth-js/dist/module/GoTrueClient.js:403` → `node_modules/@supabase/auth-js/dist/module/GoTrueClient.js:3320` → `node_modules/@supabase/auth-js/dist/module/GoTrueClient.js:421` → `apps/web/src/app/session.ts:27`
- **Lower-trust principal:** An attacker with their own Hoppin account sends a link carrying their own session tokens to a victim who is already signed in.
- **Conditions:** user_interaction: A victim who is already signed in to Hoppin in the browser opens an attacker-crafted Hoppin URL with token parameters in the fragment or query string. authentication_level: The attacker holds a valid access and refresh token for an account of their own in the same Supabase project. third_party_dependency: supabase-js/auth-js v2 defaults (2.119.0 installed, 2.118.0 locked) with implicit flowType and detectSessionInUrl enabled.
- **What happens:** The web client is created with the supabase-js defaults: implicit flow, with sessions read from the URL. On every page load, auth-js reads the fragment and the query string of the current URL. If an access_token parameter is present, it treats the page as an implicit-grant callback. It checks the token only with GET /auth/v1/user, then saves the URL session over whatever session is already stored and fires SIGNED_IN. An attacker can sign in to their own Hoppin account and put their own reusable access/refresh token pair into a link to any Hoppin route (for example /trips#access_token=...&refresh_token=...&expires_in=3600&token_type=bearer, or the same parameters in the query string of /join/<token>). A victim who is already signed in and opens the link is switched to the attacker's account with no prompt. Anything the victim then creates (personal documents, expenses, itinerary items, profile data) is stored under the attacker's account, which the attacker can read with their own login. The app never needs this path, because all of its email links use token_hash on /auth/confirm with an explicit verifyOtp call.
- **Root cause:** createSupabaseClient calls createClient(url, anonKey) without auth options, so detectSessionInUrl defaults to true and flowType to 'implicit' (auth-js GoTrueClient.js:19,21). In _initialize, auth-js accepts bearer tokens from any URL with no state, nonce or binding to a flow this browser started, and _saveSession overwrites the existing stored session.
- **Bounded local reproduction:** In the network-less node:20 sandbox, mock window (location, history), document, localStorage, WebSocket and fetch. The mock GET /auth/v1/user maps dummy JWTs to user ids 1111... (victim) and 2222... (attacker). Store a victim session (user 11111111-1111-4111-8111-111111111111, refresh_token victim-refresh) under sb-dummyref-auth-token. Set window.location.href to a payload URL, then call createClient('http://dummyref.supabase.local','dummy-anon-key') from /target/node_modules/@supabase/supabase-js/dist/index.mjs with no options, matching apps/web/src/lib/supabase.ts:17. Subscribe to onAuthStateChange, call getSession(), and read back the stored session. As a control, repeat with { auth: { flowType: 'pkce', detectSessionInUrl: false } }.
- **Actual result:** With default options, both payloads gave the same result: flowType was implicit and detectSessionInUrl was true. getSession() returned user 22222222-2222-4222-8222-222222222222 (the attacker), storage held refresh_token attacker-refresh, and the events were INITIAL_SESSION:2222... then SIGNED_IN:2222.... The only network call was GET /auth/v1/user. In the query-string variant the tokens stayed in the URL. With the proposed options, the victim's session (1111..., victim-refresh) was kept and no network call was made.
- **Smallest fix:** Turn off session pickup from the URL and use PKCE. The app signs people in only by password and by token_hash verification on /auth/confirm. Add a regression test in which a stored session survives a page load whose URL carries another account's tokens. (proposed change in `apps/web/src/lib/supabase.ts`; full code in FINDINGS-DETAIL.md)

### 4.2 Client-supplied documents.storage_path lets any authenticated user who knows an object path (including removed members and demoted organizers) read other trips' and other members' private files

- **Severity:** medium (likelihood medium: The attacker needs a full object path containing a random UUID, normally learned during legitimate prior access. Removal and demotion are routine product flows, and the exploit itself is a single direct PostgREST insert after create_trip. Impact high: Indefinite unauthorized reads of private travel documents, including shared tickets and other members' personal passport and visa scans, after access was explicitly revoked or for users who were never members.)
- **Confidence:** high — The source trace is complete, and an independent bounded PGlite reproduction against the real migrations showed the result with before and after controls on the insert and update paths. The only external assumption is that hosted Supabase Storage enforces the same storage.objects SELECT RLS for download and createSignedUrl.
- **Fingerprint:** `hoppin:documents.storage_path-unbound:storage-select-trusts-any-visible-row`
- **Source:** `supabase/migrations/001_core.sql:248` → `supabase/migrations/001_core.sql:250` → `supabase/migrations/001_core.sql:243` → `supabase/migrations/008_storage.sql:37`
- **Lower-trust principal:** A trip member who is later removed (or an organizer who is later demoted), or any authenticated user holding a leaked object path, who wants to read a private trip-documents object they are no longer, or were never, entitled to.
- **Conditions:** authentication_level: The attacker has a Supabase account (an authenticated JWT) and can call PostgREST and Storage directly. authorization_role: The attacker is an approved member of at least one trip in which to plant the row. Any authenticated user gets this through create_trip. No membership in the victim trip is needed at the time of the read. data_state: The attacker knows the target object's full path (<trip>/<uploader>/<doc uuid>-<name>). They can learn it while an approved member (shared documents) or an organizer (personal documents), or from any other leak of storage_path. Random document UUIDs make blind guessing infeasible. system_configuration: Hosted Supabase Storage evaluates the storage.objects SELECT RLS policy under the caller's JWT for download and createSignedUrl. This matches the local stub, but the Storage API was not exercised locally.
- **What happens:** The storage read policy for the private trip-documents bucket allows a read whenever any documents row the caller can see has a storage_path equal to the object name. The documents insert and update policies never tie storage_path to the row's own trip or owner folder. So any authenticated user can call create_trip to get a trip they are an approved member of, insert a documents row there (or rewrite storage_path on their own existing row) pointing at any object path, and then pass the select policy for that object. Both download and createSignedUrl rely on that policy. Paths are shown to approved members for shared documents and to organizers for personal documents. As a result, remove_member, leave_trip and set_member_role demotion do not revoke file access for anyone who kept the paths, and the access lasts indefinitely. Anyone else who obtains a path, even a user who was never a member, gets the same access. Exposed files include shared tickets and other members' personal documents such as passport scans.
- **Root cause:** documents_insert (001_core.sql:248-249) checks only is_approved_member(trip_id) and owner_id = auth.uid(). documents_update (001_core.sql:250-252) does not limit which columns can change. storage_path (001_core.sql:63) is free text with no check constraint or trigger, and no later migration changes these policies. trip_documents_select (008_storage.sql:33-40) accepts `exists (select 1 from public.documents d where d.storage_path = name)` without requiring d.trip_id to equal the object's folder[1] trip, or d.owner_id to equal its folder[2] uploader.
- **Bounded local reproduction:** In the no-network sandbox, load supabase/test/bootstrap.sql and then every supabase/migrations/*.sql file in sorted order into PGlite. As superuser, seed dummy users O (organizer), M and P (approved members) of trip B, plus outsider X. Add storage.objects rows and documents rows for a shared object B/O/<d1>-ticket.pdf and a personal object B/P/<d2>-passport.pdf. Impersonate each user with `set local role authenticated` and `request.jwt.claim.sub`. As O, call remove_member(B, M), then confirm M can no longer read the shared object (0 rows). As M, call create_trip, insert a documents row in the new trip whose storage_path is the trip B shared object name, and select the object again. As X, check that the personal object is unreadable (0 rows). Then call create_trip, plant a row pointing at the personal object, and select it again. As M, update the storage_path of the planted row to the personal object path, then select that object.
- **Actual result:** Removed member M: 0 rows before planting and 1 row after. Outsider X, never a member of trip B: 0 rows for P's personal passport object before planting and 1 row after. Update path: M read P's personal object (1 row) after rewriting storage_path. The control check that M as an approved member could not read P's personal object returned 0. Recorded in evidence-1.txt.
- **Smallest fix:** Bind every documents row to its own trip and uploader folder when it is written, make storage_path and trip_id immutable, and make the storage select policy require that the matching documents row belongs to the object's own trip folder. A row in another trip, or one pointing at another uploader's folder, can then never authorize a read. (proposed change in `supabase/migrations/016_document_path_binding.sql`; full code in FINDINGS-DETAIL.md)

### 4.3 Unvalidated items.tz lets any trip member poison the shared digest job and the trip's Days screen

- **Severity:** medium (likelihood medium: It needs only two ordinary accounts and direct PostgREST writes with the public anon key and a user JWT. The 50 trips needed for global starvation are cheap to script. Breaking a single trip needs only approved membership. Impact medium: In-app and email change notifications stop persistently, across tenants, for every trip queued after the poisoned ones, until an operator fixes the data in SQL. Co-members of a poisoned trip also lose the Days screen. There is no data disclosure or integrity loss.)
- **Confidence:** high — I ran the repository's own sendDigests, digest.ts and time.ts (with only TypeScript type syntax removed) against the real migrations in PGlite. This showed schema acceptance, the per-trip catch without record_digests, FIFO re-claiming, and victim starvation versus the control. Remaining fidelity gaps: index.ts was wired by mocks rather than run in Deno, production uses Postgres 17 and hosted Supabase rather than PGlite, and no browser was available for the DaysScreen render. Hosted default privileges only widen access, and Deno's V8 Intl rejects unknown zones the same way.
- **Fingerprint:** `supabase/migrations/001_core.sql:items.tz-unvalidated-timezone`
- **Source:** `supabase/migrations/001_core.sql:214` → `supabase/migrations/001_core.sql:37` → `supabase/migrations/009_trip_delete.sql:10` → `supabase/migrations/006_notifications.sql:118` → `supabase/functions/send-digest/index.ts:16` → `packages/core/src/digest.ts:134` → `supabase/functions/send-digest/run.ts:126` → `packages/core/src/digest.ts:171` → `packages/core/src/digest.ts:156` → `supabase/functions/send-digest/run.ts:143`
- **Lower-trust principal:** An authenticated user who can create trips, invite a second account they control, and write items through PostgREST with their own JWT.
- **Conditions:** authentication_level: The attacker has two ordinary signed-up accounts. A creates trips with create_trip and so becomes organizer. B joins through create_invite, redeem_invite and approve_member. For the trip-local Days screen impact, approved membership in the victim trip is enough. data_state: Each poisoned trip has at least one approved member other than the writer whose email_digest is on (the default), so the email render path runs. Starving all other trips requires at least MAX_TRIPS (50) poisoned trips. Only trips whose pending_since is newer than the poisoned trips' are blocked. system_configuration: send-digest is deployed with MAX_TRIPS=50 and scheduled by pg_cron as documented in supabase/ops/schedule-digest.sql. Deno uses the same V8 Intl, which rejects unknown zones.
- **What happens:** items.tz and items.end_tz accept any string. Only the client ItemForm checks that the value is a real IANA zone. Any approved member can insert or update an item with an invalid zone directly through PostgREST, because authenticated has INSERT/UPDATE on items and the RLS policies check only membership and ownership. When send-digest builds the email for a recipient who has email on, describeChange calls when(), and new Intl.DateTimeFormat({timeZone}) throws RangeError. sendDigests catches this per trip before record_digests runs, so the trip's through_id and pending_since never advance. claim_digest_batch hands out trips oldest pending_since first, capped at MAX_TRIPS=50 per run, so a poisoned trip is claimed again first on every run. An attacker with two accounts and 50 self-created poisoned trips therefore takes every claim slot. No trip whose pending change is newer than the poisoned ones ever gets in-app or email digests. Recovery needs operator SQL. Within the affected trip, the same value also makes planZone throw during DaysScreen render, and no error boundary exists in apps/web/src.
- **Root cause:** items.tz (001_core.sql:37) and items.end_tz (011_end_tz.sql:3) are unconstrained text. Every consumer passes the value unchanged to Intl.DateTimeFormat({timeZone}), which throws on an unknown zone (digest.ts when; time.ts offsetMs/formatTime). In send-digest, a render failure is caught per trip without advancing or quarantining the trip (run.ts:143-146). The claim query is global FIFO by pending_since with a fixed per-run cap (006_notifications.sql:113-119; index.ts:16). A persistently failing trip therefore becomes a permanent head-of-line blocker for every tenant, not an isolated failure.
- **Bounded local reproduction:** In the sandbox, load supabase/test/bootstrap.sql and every supabase/migrations/*.sql into PGlite. Load the repository's run.ts, digest.ts and time.ts with only TypeScript type syntax removed. As authenticated user A, call create_trip three times. For each trip, A calls create_invite, B calls redeem_invite, and A calls approve_member for B. Then A inserts the payload item into each trip. As victim organizer V, create a separate trip with approved member W and insert a normal item with tz 'Asia/Kolkata'. As superuser, simulate elapsed time: set change_log.changed_at and digest_queue.pending_since 2 hours back for the attacker trips and 1 hour back for the victim trip. Call the real sendDigests twice. Its claim step runs claim_digest_batch(300, 3, 500) as service_role, its record step runs record_digests as service_role, and sendEmails is mocked. Then run it once more with p_max_trips=4 as a control.
- **Actual result:** All three inserts of tz 'Not/AZone' were accepted. On both runs with p_max_trips=3, sendDigests reported {trips:3, notified:0, emailed:0, failedTrips:3}. record_digests was never called, and the job logged 'a trip could not be processed; it stays waiting for the next run' three times. digest_queue kept through_id=0 and pending set for every trip, including the victim trip, and the notifications table had 0 rows. The control run with p_max_trips=4 processed 'Victim trip' (notified 1, emailed w@example.test, through_id 4). The repository's time.ts planZone with the poisoned item threw 'RangeError: Invalid time zone specified: Not/AZone' (node v20.20.2).
- **Smallest fix:** Constrain tz and end_tz to valid IANA names in the database, and clean up existing rows. Make the digest renderer fall back to UTC for an unusable zone. Quarantine or advance trips that fail repeatedly, so one trip cannot hold the head of the queue. Guard client zone formatting, or add an error boundary around it. (proposed change in `supabase/migrations/016_item_tz_check.sql`, `packages/core/src/digest.ts`; full code in FINDINGS-DETAIL.md)

### 4.4 One user can stop notifications for every other trip by filling the global digest queue with trips that always fail

- **Severity:** medium (likelihood medium: The attack needs only an ordinary account, a second self-controlled account, and about 200 cheap RPC and insert calls. It needs no role in any victim trip, and the schema already accepts the invalid tz input that makes processing throw. Impact medium: Every other tenant loses in-app notification records and digest emails, which is a cross-tenant availability effect on a feature that is not safety-critical. It lasts until an operator, or the attacker, removes the failing rows. No data is disclosed or corrupted.)
- **Confidence:** high — The global ordering and limit, the fixed MAX_TRIPS, and the failure path that never records are all visible in source. The end-to-end local run executed the real sendDigests and digest.ts logic against the real SQL functions and showed the victim excluded in every run. The throw depends on V8 Intl behaviour, which Node and Deno share.
- **Fingerprint:** `supabase/migrations/006_notifications.sql:claim_digest_batch:global-oldest-first-no-tenant-fairness-no-failure-quarantine`
- **Source:** `supabase/migrations/013_trip_destination.sql:14` → `supabase/migrations/001_core.sql:214` → `supabase/migrations/006_notifications.sql:71` → `supabase/migrations/006_notifications.sql:115` → `supabase/functions/send-digest/index.ts:38` → `supabase/functions/send-digest/run.ts:126` → `supabase/functions/send-digest/run.ts:144`
- **Lower-trust principal:** An ordinary authenticated user, with a second account they control, using direct PostgREST and RPC access only inside their own trips.
- **Conditions:** authentication_level: The attacker is an ordinary signed-in user. They need no role in any victim trip. data_state: For the full starvation shown here, the attacker needs about 50 trips. Each needs a shared item that makes processing throw, for example an invalid items.tz, which is also tracked under its own tz-validation fingerprint. Each also needs another approved member with email_digest on and a non-null email, for example the attacker's second account that redeemed the attacker's invite and was approved. timing_dependency: The attacker's pending changes must be older than the victim's. They stay that way for good once the attacker's trips are queued first, because failing trips never get a new pending_since.
- **What happens:** The send-digest job handles at most 50 trips per 5-minute run. It takes them from one global queue, oldest pending change first. There is no per-owner or per-tenant share and no quarantine for trips that keep failing. Any signed-in user can create as many trips and items as they like. If processing a trip throws, its queue row is never advanced and it keeps its oldest-first slot. One example is a shared item with an invalid items.tz plus a second approved member who has email on, such as the attacker's own second account. About 50 such trips take every slot in every run. No other tenant then gets in-app notification records or digest emails until the attacker's rows are fixed or deleted. When nothing fails, the queue is still a single global FIFO with a fixed 50-trips-per-run budget. A principal who keeps more than 50 trips writing in every window can therefore stretch every other tenant's notification delay, but that path needs sustained writes and was not reproduced here.
- **Root cause:** claim_digest_batch (006_notifications.sql:114-120) selects ready trips globally by pending_since with only a global LIMIT p_max_trips, which index.ts fixes at 50. The claim has no per-owner or per-tenant partitioning and no failure or attempt state. ### 4.6 Anonymous callers can fill the sign-up queue with arbitrary third-party emails that the operator's hourly job then invites

- **Severity:** medium (likelihood high: It needs no authentication, uses only the public anon key, and is trivially scriptable. About max_waiting (default 2000) RPC calls fill the queue, and no per-requester bound exists in source. Impact medium: The sign-up overflow path is denied for as long as the queue stays full; recovery takes operator SQL or roughly 200 hourly drains at the defaults. The invite sink is visible in source. The GoTrue invite send, deployed gateway or WAF rate limits on the Data API, and the live schedule could not be observed locally. They could reduce the fill rate but not remove the missing binding.
- **Fingerprint:** `supabase/migrations/014_signup_queue.sql:join_signup_queue-anon-unbound-enqueue`
- **Source:** `supabase/migrations/014_signup_queue.sql:140` → `supabase/migrations/014_signup_queue.sql:66` → `supabase/migrations/014_signup_queue.sql:75` → `supabase/functions/drain-signup-queue/index.ts:28` → `supabase/functions/drain-signup-queue/index.ts:33`
- **Lower-trust principal:** Unauthenticated web client holding the public anon key, calling the PostgREST RPC as the anon role.
- **Conditions:** authentication_level: None: only the public anon key, which ships in the web app, is needed. system_configuration: Migration 014 is applied, and drain-signup-queue is deployed and scheduled hourly as documented. No Data API rate limit, CAPTCHA or WAF in front of /rest/v1/rpc/join_signup_queue is visible in source. - **What happens:** Migration 014 grants anon EXECUTE on the SECURITY DEFINER function join_signup_queue. The function accepts any syntactically valid address that has no account and no queue row yet, with a display name of up to 80 characters. It checks nothing else except one global count of waiting rows against max_waiting (default 2000). Nothing ties the call to a real GoTrue email-rate-limit event, to ownership of the address, or to a per-requester bound. After that, every legitimate overflow sign-up is refused with 'full', and status stays 'none' for those people. At the defaults, 2000 rows take about 200 hours to drain. A queued third-party address also makes the normal UI sign-up for that address show 'in queue' instead of calling signUp, until the row is invited.
- **Root cause:** The rule 'queue only when the email service reports it is over its limit' is enforced only in client code (AuthForm.tsx calls joinQueue only after a rate-limited signUp error). The anon-granted RPC join_signup_queue has no proof of address ownership, no per-requester or per-IP throttle, and no tie to a server-side rate-limit event. Its only bound is a global capacity counter that one requester can exhaust. The drain job then treats every queued row as a consenting sign-up.
- **Bounded local reproduction:** In the sandbox, load supabase/test/bootstrap.sql and every supabase/migrations/*.sql file in sorted order into PGlite. Grant only USAGE on schema public to anon, authenticated and service_role, with no Supabase default privileges. Set signup_queue_settings.max_waiting = 3 as a bounded stand-in for 2000. As role anon, call join_signup_queue for three third-party addresses with chosen display names, then once for a case-variant duplicate. As role anon, call join_signup_queue for a legitimate address, then signup_queue_status for that address. As role anon, try a direct insert into signup_queue, an update of signup_queue_settings, and a call to claim_signup_queue. As service_role, call claim_signup_queue(), which is the input the drain job passes to inviteUserByEmail.
- **Actual result:** anon had EXECUTE on join_signup_queue. All three third-party addresses returned 'queued', and the case-variant duplicate returned 'already_queued'. The legitimate join then returned 'full', and its status stayed 'none'. anon was denied the direct insert into signup_queue, the update of signup_queue_settings, and the call to claim_signup_queue. service_role claim_signup_queue returned exactly the three attacker-supplied emails with display names 'Chosen Name 0' to 'Chosen Name 2'. drain-signup-queue index.ts:33 passes those values to inviteUserByEmail. The actual invite send was not executed: no GoTrue was available and no network was allowed.
- **Smallest fix:** Do not let anon create queue rows that cause outbound mail and account creation for unverified addresses. Move enqueueing behind a server-side edge function. That function should verify a CAPTCHA token, apply per-IP and per-domain rate limits, and preferably enqueue only after it has itself observed GoTrue's over_email_send_rate_limit response for that sign-up attempt. It then calls join_signup_queue as service_role. Optionally, at drain time, cap invites per domain and leave headroom so the queue cannot consume the email budget needed for password resets. (proposed change in `supabase/migrations/016_signup_queue_lockdown.sql`; full code in FINDINGS-DETAIL.md)

### 4.12 Concurrent cast_vote calls can give one member several votes on a single-choice poll

- **Severity:** low (likelihood medium: Any approved member can trigger it alone, using their own session and two parallel RPC requests. It depends on landing inside a short overlap window, which was reproduced locally but not measured on the hosted pool. Impact low: The damage is limited to poll integrity inside a trip the attacker already belongs to. They can add at most one extra vote per option (at most 10 options) on a single-choice poll. Adding votes to several options does not concentrate weight on any one of them, and there is no cross-tenant access or privilege change.)
- **Confidence:** high — The flaw is visible in the source and was reproduced in real multi-connection Postgres 16 at READ COMMITTED (Supabase's default isolation level), with controls ruling out the single-call and sequential paths. The remaining uncertainty is how easy the overlap is on hosted PostgREST/Postgres 17; nothing there changes the locking behavior.
- **Fingerprint:** `supabase/migrations/012_polls.sql:cast_vote:single-choice-race-no-unique-voter`
- **Source:** `supabase/migrations/012_polls.sql:116` → `supabase/migrations/012_polls.sql:123` → `supabase/migrations/012_polls.sql:131` → `supabase/migrations/012_polls.sql:141` → `supabase/migrations/012_polls.sql:142`
- **Lower-trust principal:** An approved member of a trip, using their own session, on an open single-choice poll in that trip.
- **Conditions:** authentication_level: The caller must be authenticated as an approved member of the poll's trip. data_state: The poll must be open (closed_at is null) and single-choice (multiple = false), with at least two options. timing_dependency: The two cast_vote calls must overlap: the second call's DELETE has to run before the first call's transaction commits. In hosted PostgREST each RPC is its own transaction on a pooled connection, so parallel requests must land inside that window. The window was reproduced locally but not measured against the deployment.
- **What happens:** cast_vote enforces single choice only within one call. It checks that the call names at most one option, deletes the caller's existing votes for the poll, then inserts the new one. poll_votes has no unique (poll_id, user_id) constraint, and the function takes no lock on the poll or on the caller's votes. Under READ COMMITTED, a second overlapping call's DELETE cannot see the first call's uncommitted row. Its INSERT also does not conflict, because the primary key (poll_id, option_id, user_id) differs. Both transactions commit, so one approved member ends up with a vote on each option on a poll that allows one. tallyPoll counts every row, so each option gets +1 from that member. The extra votes can only be one per option, and they stay until that member votes again one call at a time.
- **Root cause:** The single-vote-per-member invariant on non-multiple polls is a check-then-act sequence (delete, then insert) inside a SECURITY DEFINER function. Nothing backs it: no row lock (the poll is read without FOR UPDATE), no advisory lock, and no uniqueness or exclusion constraint on (poll_id, user_id) for single-choice polls.
- **Bounded local reproduction:** Inside the run-pg.sh sandbox (Postgres 16, no network), load supabase/test/bootstrap.sql and all migrations in sorted order. Insert two dummy auth.users rows. Call create_trip as the organizer, add the second user as an approved member, and create a single-choice poll with options A and B. Controls: as the member, call cast_vote with {A,B}, which is rejected. Then vote A, then B, one after the other, which leaves 1 row. Withdraw the vote, then run session 1 (vote A and hold the transaction open) in the background. While it is open, run session 2 (vote B), and let both commit. Count poll_votes rows for (poll, member), and read the tally as the organizer.
- **Actual result:** Session 2 committed at 06:04:54 while session 1 was still open, and session 1 committed at 06:04:56. Both returned without error. poll_votes then held 2 rows for the member (options A and B) on a poll with multiple=false. The single-statement overlap gave the same 2 rows, and the organizer's RLS-visible tally showed A=1, B=1 from that one member.
- **Smallest fix:** Serialize votes per poll inside cast_vote so the delete-then-insert is atomic, by locking the poll row before checking and replacing votes. The lock also covers the race with close_poll. Optionally add a constraint trigger, or a unique (poll_id, user_id) index for single-choice polls only (for example via a denormalized multiple column), as a second line of defense. (proposed change in `supabase/migrations/016_cast_vote_lock.sql`; full code in FINDINGS-DETAIL.md)

## 6. Hardening notes (not findings)

- No Cloudflare Pages _headers file exists, so the app ships without Content-Security-Policy, frame-ancestors or X-Frame-Options, Strict-Transport-Security, Referrer-Policy or X-Content-Type-Options. Adding apps/web/public/_headers with at least frame-ancestors 'none', HSTS and nosniff would harden against framing and protocol downgrade.
- The hosted Supabase auth redirect allowlist includes http://localhost:5173/** and http://localhost:4173/** alongside production origins (docs/deploy.md:8,32). Production auth email links could be pointed at a localhost listener on the recipient's machine. Keep localhost only in the dev project.
- The .gitignore pattern .env.* also ignores any .env.example. readSupabaseEnv's error tells users to copy apps/web/.env.example, which is not tracked. Add !.env.example (or rename it) so the template can be committed, and consider adding *.pem, *.key and credentials*.json patterns defensively.
- scripts/release.mjs:58 passes the merged .env.release and process.env (including SUPABASE_ACCESS_TOKEN and CLOUDFLARE_API_TOKEN) to every child process, including the vite build and tests. Vite exposes only VITE_* variables to the bundle, so there is no leak today, but passing per-command minimal env would limit token exposure to child tooling.
- The /gallery design-preview route ships in production builds (apps/web/src/app/routes.tsx:30). It uses only stubs today, but the route should be gated behind import.meta.env.DEV so future preview code cannot reach real services.
- Anyone signed out can put any email address on the sign-up waiting list with a display name they choose (supabase/migrations/014_signup_queue.sql:58-83). That name becomes the person's profile name when the queue invites them (supabase/functions/drain-signup-queue/index.ts:32-35). The app's waiting-list check also stops that person from signing up normally (apps/web/src/components/AuthForm.tsx:106-107). Fix: drop the queued display_name from invite metadata, or let the person's own sign-up go ahead even when a queue row exists.
- Private items deleted by delete_my_account or leave_trip stay in change_log as before/after JSON copies, including details (supabase/migrations/009_trip_delete.sql:8-19, supabase/migrations/010_account.sql:114-115). Fix: in delete_my_account, delete change_log rows where item_owner_id = me and item_visibility = 'private'.
- apps/web/src/lib/pdf-text.ts:98: tesseract.js `corePath` and `langPath` default to cdn.jsdelivr.net, so third-party JS/wasm runs via importScripts inside a worker on the app origin, with IndexedDB access and no SRI or CSP. Self-hosting tesseract-core and eng.traineddata as Vite `?url` assets and passing `corePath`/`langPath` explicitly would remove the runtime CDN trust and the first-use network dependency.
- apps/web/functions/api/expand-map-link.ts:16: the public 200 response has no `Vary: Sec-Fetch-Site`. A shared cache could therefore return it to cross-site callers, bypassing the same-site check at line 12. The data is public, but adding `Vary: Sec-Fetch-Site` or using `cache-control: private` would keep the check effective as a usage control.
- apps/web/src/lib/expand-map-link.ts:33: `allowedHost` accepts any port and plain `http:` on Google hosts. Requiring `https:` and an empty or 443 port would narrow the outbound surface without breaking the feature.
- The trip-documents bucket (008_storage.sql:10-12) sets no file_size_limit or allowed_mime_types. The 25 MB and PDF/image limits exist only in the client (packages/core/src/documents.ts:15-24), and contentType comes from file.type (apps/web/src/lib/documents.ts:59), so direct Storage API uploads can store any content type and size up to the project's global limit. Set file_size_limit=26214400 and allowed_mime_types to the PDF/image list on the bucket.
- Signed URLs from getDocumentUrl (apps/web/src/lib/documents.ts:102-105) stay valid for up to 300 s after a member is removed or leaves. This is acceptable but should be documented as the revocation window.
- leave_trip and delete_my_account delete documents rows in the database but depend on the client to remove storage objects first (services.tsx:200-227). A direct RPC call orphans the objects. They become unreadable to others, because the owner clause needs approved membership, but they are never deleted.
- Add a server-side check constraint (location_url ~* '^https?://') even though React 19 sanitizes javascript: in JSX hrefs. Other consumers, such as the digest email, ICS URL and print view, receive the raw value.

- ConfirmEmail redeems any token_hash in the URL, so an attacker can send a link with their own unconsumed signup token and sign a victim's browser into the attacker's account (login CSRF), and the local data is not cleared.
