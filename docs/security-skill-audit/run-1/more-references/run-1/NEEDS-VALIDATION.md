# Needs validation — prioritized leads (no severity assigned)

These are source-grounded hypotheses whose decisive fact lies outside the repository or the local sandbox. They are not confirmed vulnerabilities. Do not test them against production; use the owner-observed checks below.

## 1. Stored javascript: URL in items.location_url is placed in the raw DOM href of the map pin's 'Get directions' link

**Fingerprint:** `apps/web/src/components/map/MapView.tsx:pinCard:raw-href-location_url`

An approved trip member can write any string to items.location_url by writing straight to the table through PostgREST, with an INSERT or an UPDATE of their own shared item. The only http(s) scheme check is client-side, in ItemForm.submit. The interactive trip map (TripMap) and day map (DayMap) give each pin a card built by pinCard(). pinCard uses document.createElement('a') and sets link.href = point.directions, which is item.locationUrl unchanged. React 19.3.1's sanitizeURL protects the JSX location_url links (DayView, StopSheet, BookingDetail, NowNext), but it does not cover this raw DOM assignment. The card shows on hover, on focus, or when the pin is selected. If another member clicks 'Get directions', a browser would run the javascript: URL in the app origin with that member's Supabase session. That last step depends on browser behaviour and on the deployed headers. Neither was observed locally.

**Claimed root cause:** items.location_url is plain text with no server-side scheme constraint (supabase/migrations/001_core.sql:39). No migration or trigger adds one: after all migrations only the group_item, ends_at, kind, title and visibility CHECKs exist, and items_before_update changes only version and updated_at. pinCard (apps/web/src/components/map/MapView.tsx:161) assigns the value to a raw DOM anchor href and never checks the scheme.

### Source trace
1. **entrypoint** `supabase/migrations/001_core.sql:214` (items_insert / items_update policies) — Role authenticated has insert/update on items (line 192). items_insert lets any approved member insert their own item, and items_update (line 216) lets them update their own shared item. location_url (line 39) is unconstrained text, so a direct PostgREST write skips the ItemForm regex.
1. **propagation** `apps/web/src/data/mappers.ts:106` (itemFromRow) — row.location_url is copied verbatim to Item.locationUrl for every member who can see the shared item.
1. **propagation** `packages/core/src/stops.ts:59` (dayStops) — itemPlace(item) uses the attacker-set details.place (place.ts:126). A group item with a valid place becomes a stop on the map that every member sees.
1. **propagation** `apps/web/src/components/map/points.ts:41` (withPlanLinks) — item.locationUrl is copied to MapPoint.directions unchanged, with no scheme check.
1. **sink** `apps/web/src/components/map/MapView.tsx:161` (pinCard add()) — link.href = href on an anchor made with document.createElement('a'). React does not render it, so sanitizeURL is never applied. Clicking 'Get directions' would navigate to the stored javascript: URL in the app origin.

### Verified evidence
- `apps/web/src/components/ItemForm.tsx:120` — The only http(s) check is /^https?:\/\/\S+$/i in the form's submit handler. Direct table writes skip it.
- `supabase/migrations/001_core.sql:39` — location_url text with no CHECK. In the sandbox (PGlite, all migrations), approved dummy member MALLORY inserted a shared group item and then updated location_url to 'JavaScript:alert(document.domain)'. The update returned version 2, and approved member VICTIM read the value back unchanged along with details.place {lat:15.5, lon:73.8}. The pg_constraint dump showed no scheme check (agents/v3-01/artifacts/evidence-1.txt, if promoted; hunter's agents/w1-client/artifacts/evidence-1.txt shows the same for INSERT).
- `supabase/migrations/010_account.sql:7` — items_before_update only blocks trip_id/owner_id changes and bumps version/updated_at. It does not normalise location_url.
- `apps/web/src/components/map/MapView.tsx:166` — if (point.directions) add(point.directions, 'Get directions'). The card is appended for interactive maps (line 373) and is shown on hover, focus-within or data-open (map.css:43-46).
- `apps/web/src/components/map/TripMap.tsx:69` — The trip map applies withPlanLinks and renders the interactive MapFrame (line 130). DayMap.tsx:24 does the same (line 31).
- `node_modules/react-dom/cjs/react-dom-client.production.js:1581` — sanitizeURL replaces javascript: URLs (isJavaScriptProtocol, line 1579) in React-managed URL attributes. That protects the JSX location_url hrefs but not the imperative link.href in pinCard.
- `apps/web/index.html:3` — The head has no CSP meta tag, and the repo has no _headers file (architecture: no CSP/_headers). Response headers on the deployed Cloudflare Pages site are not visible from source.

### Exact blockers
- No browser is available in the sandbox, so clicking the pin card's 'Get directions' link and running the javascript: URL in the app origin was not observed.
- Production response headers on Cloudflare Pages could include a CSP that blocks javascript: navigation (for example script-src without 'unsafe-inline'). They are not in the repository and were not checked, since deployed endpoints are out of scope.

### Affected boundary
URL scheme validation (form-only) vs raw DOM sink

### Resolution plan
- **Local:** Use a local browser against a local dev build backed by a local Supabase with dummy users A and B, both approved members of a dummy trip. As A, create a shared group activity, then PATCH /rest/v1/items?id=eq.<id> with {"location_url":"javascript:alert(document.domain)","details":{"place":{"lat":15.5,"lon":73.8}}}. As B, open /trips/<trip>/map (or the day view's DayMap) while online with WebGL. Select or hover the pin, click 'Get directions', and confirm the alert shows the local app origin. Also confirm that the StopSheet JSX link to the same URL shows React's blocked stub instead. Stop at the alert and run no further payloads.
- **Owner-observed:** The owner checks the production HTML response headers on the Cloudflare Pages site (Content-Security-Policy, and any Pages _headers or dashboard Transform Rules) to see whether javascript: navigations are blocked. Fix regardless: add a CHECK constraint (location_url is null or location_url ~* '^https?://'), clean existing rows, and in pinCard parse the href with new URL() and only set link.href when the protocol is http: or https: (planHref is same-origin and can stay).

## 2. Anyone holding a live session can change the account password without the current password or reauthentication

**Fingerprint:** `apps/web/src/lib/auth-api.ts:updatePassword:no-reauthentication-for-signed-in-password-change`

The Account screen's 'Change password' link (AccountScreen.tsx:129) opens /reset-password, the only password route (routes.tsx:28). That page shows the new-password form for any signed-in session. The only gates are that useSession is not 'loading' or 'signedOut' (ResetPassword.tsx:20,48-56,79-105). Submit calls auth.updatePassword(password) (line 38), which sends client.auth.updateUser({ password }) (auth-api.ts:133). No current password and no reauthentication nonce are sent with it. The PasswordClient type (auth-api.ts:19) cannot carry a nonce, and the app never calls reauthenticate(). The repository's only auth-config writer, scripts/supabase-email.mjs, never enables Supabase's 'Secure password change' (security_update_password_require_reauthentication), and no supabase/config.toml exists. In source, holding a session is the only proof needed. Someone with only a session can therefore turn temporary access into lasting ownership by setting a password they know. Examples: a stolen access or refresh token taken from browser storage, an unlocked or shared device, or an XSS elsewhere. The same session can also call GoTrue PUT /auth/v1/user directly, so the UI is not the only path. Whether the deployed server allows this depends on its configuration. The bundled auth-js docs say that even with Secure password change on, a nonce is only needed when the session was created more than 24 hours ago. A fresh session can change the password regardless of the flag. When the nonce is required, it goes to the owner's email or phone, which a session thief cannot read.

**Claimed root cause:** createAuthApi.updatePassword (auth-api.ts:131-135) accepts only the new password and calls updateUser({ password }) with no nonce and no check of the current password. The PasswordClient interface (auth-api.ts:19) rules out a nonce, and the app never calls reauthenticate(). The server-side control that would require reauthentication (security_update_password_require_reauthentication) is never set by scripts/supabase-email.mjs (its 'auth' body at line 44 holds only mailer_otp_exp, password_min_length and mailer_autoconfirm). In the repository, a password change is protected only by holding a session.

### Source trace
1. **entrypoint** `apps/web/src/routes/AccountScreen.tsx:129` (AccountScreen) — The 'Change password' link sends a user who is already signed in to /reset-password.
1. **propagation** `apps/web/src/routes/ResetPassword.tsx:20` (ResetPassword) — useSession(sessionClient) is the only gate. The form renders for any session that is not loading or signed out, for any account (lines 48-105).
1. **propagation** `apps/web/src/routes/ResetPassword.tsx:38` (ResetPassword.submit) — Submits only the new password through auth.updatePassword(password). No current password or nonce is collected.
1. **sink** `apps/web/src/lib/auth-api.ts:133` (createAuthApi.updatePassword) — client.auth.updateUser({ password }) is sent with no nonce or current password. GoTrue accepts or refuses it based only on the session JWT, the session's age and the project's Secure password change setting.

### Verified evidence
- `apps/web/src/lib/auth-api.ts:19` — The PasswordClient interface types updateUser as { password: string } only, so a nonce cannot be passed through this API.
- `apps/web/src/lib/auth-api.ts:130` — The doc comment states the intent: 'Sets a new password for whoever is signed in (the reset link signs them in first).' The recovery flow and the signed-in change flow share this path without separate assurance.
- `scripts/supabase-email.mjs:44` — The 'auth' mode PATCH body sets only mailer_otp_exp, password_min_length and mailer_autoconfirm. No file in the repository (outside node_modules) mentions reauthentication or secure password change, and there is no supabase/config.toml.
- `apps/web/src/app/routes.tsx:28` — /reset-password is the only password-change route. The recovery, invite-welcome and signed-in change flows all use it.
- `node_modules/@supabase/auth-js/src/GoTrueClient.ts:3394` — The installed auth-js says that when Secure password change is enabled, updateUser needs a nonce only if the user hasn't signed in recently (session created more than 24 hours ago). reauthenticate() exists at line 2640 and sends the nonce to the user's email or phone. The app uses neither.

### Exact blockers
- The deployed Supabase project's security_update_password_require_reauthentication ('Secure password change') value is not in source. GoTrue and the Management API are not available locally, and live endpoints must not be contacted.
- Even with that flag on, the installed auth-js docs say GoTrue exempts sessions created in the last 24 hours. How GoTrue measures session age for a refreshed or stolen session is server behaviour that cannot be observed locally.
- Whether GoTrue revokes the account's other refresh tokens when the password changes (which would evict the real owner after a takeover) is server-side behaviour that is not available locally.

### Affected boundary
holder of any live session versus the account owner's password and other sessions

### Resolution plan
- **Local:** No local GoTrue is available, so the server decision cannot be reproduced here. After a fix, a unit test in apps/web/test/auth-api.test.ts with a fake PasswordClient should check the non-recovery change path. It must either call reauthenticate() and pass the user-entered nonce to updateUser({ password, nonce }), or re-verify the current password through signInWithPassword before calling updateUser. It must also refuse to call updateUser when neither proof is given.
- **Owner-observed:** The project owner reads security_update_password_require_reauthentication in Supabase Dashboard → Authentication → Providers → Email ('Secure password change'), or reads it with a read-only GET /v1/projects/{ref}/config/auth. Then, using only a dummy test account, create a session B and age it past 24 hours (or use one created more than 24 hours ago). From B, call supabase.auth.updateUser({ password: '<new dummy password>' }) without a nonce and record whether it succeeds or returns a reauthentication_needed error. Repeat from a freshly created session A. Finally, check whether a separate session C's refresh token still works after the change. Restore the dummy account afterwards.

## 3. Offline trip cache and device key survive any session end or account switch other than the Sign out button

**Fingerprint:** `apps/web/src/offline/db.ts:hoppin:not-cleared-on-session-change`

The app keeps trip snapshots, document blobs, the device key and queued changes in one IndexedDB database named 'hoppin', shared by everyone who uses the same browser origin. Only two places clear it: the explicit Sign out handler and Delete account. Sessions also end without that button. In the bundled auth-js 2.119.0, a refresh-token failure after the access token has expired, or a revoked session found by getUser, calls _removeSession and emits SIGNED_OUT. Opening an emailed /auth/confirm link while signed in replaces the session with another account and emits SIGNED_IN. In every one of these cases useSession only updates React state. RequireSession then gives the new userId to the trip screens. useTrip shows getLocalTrip(tripId) at once, and tripGate checks only the load phase. It never checks whether the viewer appears in the cached snapshot's members. So the next account on the same browser profile can open /trips/<A's trip id> and see A's cached itinerary, members, expenses and shared-document metadata. This lasts indefinitely while offline. When online, it lasts until syncTrip gets no-access and wipes the trip. Queued writes are narrower. flushOutbox first fetches the snapshot with the new JWT and stops on no-access (outbox.ts:194), so A's queued changes are sent only if B is also an approved member of that trip. Even then, RLS rejects A's queued creates (owner_id = auth.uid()), which become drafts. A's queued 'I'm in' RSVPs are also rejected (user_id = auth.uid()) and are dropped from the outbox with a notice. A's queued 'I'm out' RSVPs become a delete that RLS filters to zero rows without an error, so they are silently counted as sent. A's queued field edits and queued deletes are sent under B's identity and are limited only by B's edit rights (can_edit_item). Personal-document blobs stay in the database along with the device key. cacheDocuments and visibleDocuments filter by viewer, so the UI path to show them to B was not shown. Anyone with direct access to the browser profile can read IndexedDB anyway, as the crypto.ts comment admits. The practical gap is that the app's own sign-out clearing does not run on implicit or remote session ends.

**Claimed root cause:** The offline database is not bound to the signed-in user. useSession reacts to auth state changes only by setting React state. Nothing clears or partitions local data on SIGNED_OUT or when the user id changes.

### Source trace
1. **entrypoint** `apps/web/src/app/session.ts:27` (useSession) — Every onAuthStateChange event, including SIGNED_OUT from auth-js _removeSession and SIGNED_IN as a different user from verifyOtp, is only mirrored into React state. clearAllLocalData is never called.
1. **propagation** `apps/web/src/routes/RequireSession.tsx:17` (RequireSession) — The new session's userId goes straight to the trip screens through UserContext, with no check against who wrote the local data.
1. **propagation** `apps/web/src/offline/db.ts:48` (openOfflineDb) — One fixed database name 'hoppin' for all users. sharedOfflineDb (line 54) is the single instance used by the app (services.tsx:126).
1. **propagation** `apps/web/src/app/useTrip.ts:164` (useTrip read effect) — getLocalTrip and the outboxes for the URL tripId are loaded and set as the visible snapshot at line 170, before any server check and whatever the viewerId.
1. **sink** `apps/web/src/app/trip-data.tsx:24` (tripGate) — The trip screens render whenever phase is 'ready', meaning a local copy exists. The viewer does not need to be a member of the cached snapshot.

### Verified evidence
- `apps/web/src/app/useSignOut.ts:10` — clearAllLocalData runs only in the explicit sign-out handler, which is documented as removing every trip and document from the device first. That is the intended invariant.
- `apps/web/src/routes/AccountScreen.tsx:74` — The only other call to clearAllLocalData is in delete-account.
- `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:4379` — auth-js 2.119.0 calls _removeSession on a non-retryable refresh failure once the access token has expired.
- `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:4501` — _removeSession emits SIGNED_OUT, which the app handles only by updating React state.
- `apps/web/src/offline/crypto.ts:23` — The device key used for personal-document blobs is stored in the same database and is not cleared on implicit session end.
- `apps/web/src/offline/sync.ts:24` — Trip data is wiped only when an online syncTrip returns no-access. That is too late for offline viewing, and it is the only wipe path besides sign-out and delete-account.
- `apps/web/src/offline/outbox.ts:194` — flushOutbox stops on no-access before sending, so the previous user's queued writes reach the server only when the new user is also a member of the trip.
- `apps/web/src/offline/outbox.ts:229` — Queued deletes are sent with writer.deleteItem under the current JWT, so A's queued removals run as B, limited by B's edit rights. Queued field edits do the same through writer.updateItem at line 265.
- `apps/web/src/offline/outbox.ts:284` — Queued RSVPs are sent with the stored userId (A). A rejected 'I'm in' insert is dropped from the outbox and only a notice is recorded (lines 290-293). An 'I'm out' delete for A matches zero rows under B's JWT without an error (writes.ts:57), so it is counted as sent with no notice.
- `supabase/migrations/001_core.sql:215` — The items insert RLS policy requires owner_id = auth.uid(), and rsvps_insert at line 236 requires user_id = auth.uid(). So A's queued creates and 'I'm in' RSVPs are rejected under B's JWT.

### Exact blockers
- No browser is available in the approved sandbox, so a real IndexedDB plus React run was not executed. That run would show A's cached trip rendering for account B after an implicit SIGNED_OUT or an account switch through the confirm link.

### Affected boundary
cache clearing on sign-out, account switch, removal; login CSRF / session fixation into attacker-owned account

### Resolution plan
- **Local:** In a local browser against a local Supabase with dummy accounts A and B: sign in as A, open one of A's trips so it is cached, and while offline queue one field edit and one delete of a shared plan. Without pressing Sign out, end A's session in one of two ways. Either expire the access token and revoke A's refresh token server-side, then wait for the SIGNED_OUT event. Or, while signed in as A, open a /auth/confirm?token_hash=...&type=signup link issued for B. Sign in as B if needed. Go offline, open /trips/<A trip id>/days, and record whether A's itinerary renders. Check in DevTools that the 'hoppin' IndexedDB still holds A's trips, blobs and device-key rows. Then go online. If B is not a member, confirm the trip is wiped after syncTrip and no outbox write is sent. Repeat with B as an approved member of the same trip who has edit rights. Confirm that A's queued field edit and delete are applied as B, that A's queued create becomes a draft, that A's queued 'I'm in' RSVP is dropped with a notice, and that A's queued 'I'm out' RSVP is silently removed from the outbox.
- **Owner-observed:** Not required. Fix in source by calling clearAllLocalData(db) from the onAuthStateChange handler on SIGNED_OUT and whenever session.user.id differs from an owner id stored in the meta table. Alternatively, name the database per user id, for example openOfflineDb(`hoppin-${userId}`), and delete other users' databases.

## 4. Shared document cached offline is reopened as a same-origin blob: URL using the uploader-chosen content type (possible stored XSS)

**Fingerprint:** `apps/web/src/offline/sync.ts:getLocalDocument:stored-contentType-blob`

Every approved member's client caches every shared trip document on each sync, along with the Content-Type that Storage reports for the download. When a document is opened later, getLocalDocument rebuilds it as new Blob([data], {type: storedContentType}). Docs.tsx and ItemScreen.tsx then pass URL.createObjectURL(blob) to openFile, which sends a new tab to that blob: URL. A blob: URL belongs to the app origin. A member could upload an object with Content-Type text/html or image/svg+xml directly to their own Storage folder, through the Storage API so the client validator is skipped, and then insert a shared documents row that points at it. If Storage returns that type on authenticated download, script in the file could run in the app origin for any other member who opens the document from the cache. That script could read the victim's Supabase session from localStorage and use the device key stored in IndexedDB. The online fallback is not affected: it opens a signed URL on the Supabase Storage origin, not the app origin.

**Claimed root cause:** The content type of a member-uploaded file is trusted from upload all the way to rendering. The trip-documents bucket is created without allowed_mime_types. The client validator accepts a file if either its type or its extension is allowed, and it can be skipped entirely by calling the Storage API directly. document-source.download keeps the server-reported Blob type, and getLocalDocument rebuilds the blob with that stored type before it is opened at the top level in the app origin. There is no allowlist and no forced download when the file is reopened.

### Source trace
1. **entrypoint** `supabase/migrations/008_storage.sql:25` (trip_documents_insert) — An approved member can insert any object under <trip>/<self>/ in trip-documents. The bucket is created at line 10 with only id, name and public, so there is no allowed_mime_types and no file_size_limit.
1. **propagation** `apps/web/src/app/useTrip.ts:130` (round) — After every successful sync, round calls cacheDocuments for the viewer automatically, with no user action.
1. **propagation** `apps/web/src/offline/sync.ts:59` (cacheDocuments) — wanted includes every shared document visible to the viewer, whoever uploaded it.
1. **propagation** `apps/web/src/data/document-source.ts:17` (download) — contentType is set to data.type, the type of the downloaded Blob, which comes from the Storage response's Content-Type. It falls back to application/octet-stream only when the type is empty.
1. **propagation** `apps/web/src/offline/sync.ts:78` (cacheDocuments) — That contentType is saved unchanged in the IndexedDB blobs record (shared documents are not encrypted).
1. **propagation** `apps/web/src/offline/sync.ts:95` (getLocalDocument) — The blob is rebuilt as new Blob([data], { type: record.contentType }), with no allowlist.
1. **propagation** `apps/web/src/routes/Docs.tsx:82` (open) — The cached blob is turned into URL.createObjectURL(stored), a blob: URL in the app origin. ItemScreen.tsx line 43 (openDocument) does the same.
1. **sink** `apps/web/src/lib/open-file.ts:25` (openFile) — The new tab, opened as about:blank, is sent to the blob URL with tab.location.href = url, so the blob renders as a top-level document in the app origin. Line 24 sets tab.opener = null, but that does not change the origin of the blob document.

### Verified evidence
- `apps/web/src/lib/documents.ts:59` — The normal upload passes contentType: file.type, which the uploader controls. A direct Storage API call with the member's JWT skips uploadDocument and validateDocumentFile entirely.
- `packages/core/src/documents.ts:18` — validateDocumentFile rejects a file only if both the type and the extension are disallowed, so a text/html file named x.pdf passes. This is a client-side check only.
- `supabase/migrations/001_core.sql:248` — documents_insert only requires an approved member and owner_id = auth.uid(). scope and storage_path are free-form, so a member can publish a shared row. documents_select (line 243) shows shared rows to every approved member, and trip_documents_select (008_storage.sql line 37) lets anyone who can see the row read the object. Promoted local check agents/w1-client/artifacts/evidence-1.txt, check B: in PGlite, bob saw alice's shared row and her object.
- `apps/web/src/offline/sync.ts:60` — The cache filter keeps d.scope === 'shared' || d.ownerId === viewerId, so other members' shared uploads are cached without any type check.
- `apps/web/src/routes/ItemScreen.tsx:43` — This is the second path that opens a cached document as a same-origin blob URL (from a booking's attachments).

### Exact blockers
- Whether hosted Supabase Storage returns the stored text/html or image/svg+xml Content-Type on an authenticated download, so that supabase-js gives back a Blob with that type, cannot be observed from source. The PGlite storage stub has no metadata column and no Storage API.
- No browser is available in the sandbox, so script execution after a new tab is sent to a same-origin blob: URL with an HTML or SVG type, and the reach into localStorage and IndexedDB, could not be observed.
- The repository has no CSP or _headers file, and the headers actually served by the Cloudflare Pages deployment cannot be seen from the repository.

### Affected boundary
same-origin rendering of member-uploaded files

### Resolution plan
- **Local:** Use a local Supabase stack with dummy users A and B, both approved members of the same dummy trip. As A, call the Storage API directly to upload <trip>/<A>/<uuid>-x.svg with Content-Type image/svg+xml and the body <svg xmlns='http://www.w3.org/2000/svg' onload='document.title=origin'/>. Then insert a documents row with scope 'shared', owner_id A and that storage_path. As B, open the trip online in a local browser so cacheDocuments runs. In DevTools, check that the IndexedDB blobs record has contentType image/svg+xml. Then open the document from Docs and check that the new tab's title or console shows the app origin. Repeat with a text/html object named x.pdf. Use only a benign marker and do not read real session data.
- **Owner-observed:** On the hosted project, the owner uploads a harmless object to trip-documents with Content-Type text/html and another with image/svg+xml. As a member, download each through supabase-js and record Blob.type or the response Content-Type. Also check the headers that Cloudflare Pages serves for the app (CSP). Fix: set allowed_mime_types on the trip-documents bucket (application/pdf, image/jpeg, image/png, image/webp, image/heic, image/heif). In document-source.download or getLocalDocument, map the stored type to that allowlist and use application/octet-stream for anything else, so a disallowed file is downloaded instead of rendered in the app origin.

## 5. Anonymous pre-registration of a victim's email: clicking the confirmation link may sign the victim into an account whose password the attacker set

**Fingerprint:** `apps/web/src/routes/ConfirmEmail.tsx:signup-confirm:pre-registered-account-keeps-creator-password`

An anonymous caller can call GoTrue signUp (POST /auth/v1/signup) with a victim's email, a password the attacker picks and a display_name the attacker picks. This is the same request apps/web/src/lib/auth-api.ts:75 sends. handle_new_user (an AFTER INSERT trigger) right away creates a profiles row with the attacker's display name, and nothing else changes it later. signup_queue_status and join_signup_queue then report the email as 'registered' to anonymous callers, so the email never goes through the queue invite path, which forces a new password. GoTrue sends the victim the confirm-signup email. Its subject and copy present it as an invite ('Your Hoppin invite', 'This note is your invite to Hoppin', 'Open my invite'), though the copy also says 'hop in with the password you chose'. When the victim clicks, ConfirmEmail calls verifyOtp(type=signup). Per the code's own comments, this confirms the email and signs the victim in. ConfirmEmail then sends type=signup to pathOnly(next) and does not force a password reset. Only invite and recovery links go to /reset-password. If GoTrue issues the session and keeps the password set at sign-up, the victim ends up using an account whose password the attacker knows. The attacker could then sign in and read any trip data the victim can see. The AuthForm 'exists' screen offers a reset link, which helps only if the victim reaches it through the sign-up form; the direct link click is not covered. The verifier reproduced the database side independently in PGlite. The credential side cannot be seen in this repository.

**Claimed root cause:** Confirming a type=signup email is treated as full account ownership, but the password and profile metadata were set at signUp time by someone who never proved they own the email. Nothing replaces or resets that password when the email is confirmed. ConfirmEmail.tsx:46 sends type=signup to `next` instead of the set-password page used for invite and recovery. handle_new_user (007_invites_profiles.sql:14-31) stores the unverified metadata on INSERT only. The signup_queue functions (014_signup_queue.sql:45,69) treat unconfirmed auth.users rows as registered.

### Source trace
1. **entrypoint** `apps/web/src/lib/auth-api.ts:75` (createAuthApi.signUp) — Calls GoTrue signUp with the caller's email, password and data.display_name. An anonymous attacker can send the same POST /auth/v1/signup with a victim's email and the public anon key.

## 6. Email-confirm page signs an already signed-in user into whichever account the link's token belongs to (login CSRF)

**Fingerprint:** `apps/web/src/routes/ConfirmEmail.tsx:verifyEmailLink:replaces-existing-session-login-csrf`

The public route /auth/confirm (routes.tsx:27, outside RequireSession) reads token_hash and type from the query string. Once on mount, it calls auth.verifyEmailLink, which passes them straight to supabase.auth.verifyOtp. The page does not look at the current session. It does not compare the token's account with the signed-in user, and it does not ask the user to confirm. The installed auth-js (2.119.0) then saves the returned session unconditionally, replacing the stored one. It does not revoke the previous session. All the email templates build a bare, forwardable link of the form {{ .SiteURL }}/auth/confirm?token_hash=...&type=.... The client is created with default options (supabase.ts:17), which means the implicit flow (GoTrueClient.js:24), so nothing binds the token to the browser that requested it. An attacker can therefore request a password reset for their own account, or sign up a fresh account, and keep the emailed token_hash without using it. The attacker then sends a victim https://<site>/auth/confirm?token_hash=<attacker token>&type=recovery (or type=signup&next=/trips). If the hosted GoTrue /verify endpoint accepts that token from the victim's browser, the victim's Hoppin session is silently swapped for the attacker's account. A recovery link lands them on 'Choose a new password'. A signup link goes to the attacker-chosen same-site path in next. Anything the victim then creates (trips, items, bookings, uploaded travel documents) is written into the attacker-controlled account, where the attacker can read it. Because the offline database is not partitioned per user (linked existing root cause apps/web/src/offline/db.ts:hoppin:not-cleared-on-session-change), the victim's cached data and queued writes can also carry over. The impact needs victim interaction and is limited to data the victim enters after the swap. The UI does show the new account identity, for example on the account screen, which may alert the victim. Suggested fix: on /auth/confirm, if a session already exists, do not call verifyOtp automatically. Show 'You are signed in as X; this link is for another account — continue?'. Only after the user confirms, call signOut({scope:'local'}) (or global) and clear the offline DB, then verify.

**Claimed root cause:** ConfirmEmail.tsx treats possession of a URL token as consent to switch accounts. It calls verifyOtp on mount without checking for an existing session or comparing identities, and without asking the user to confirm. auth-js verifyOtp then calls _saveSession unconditionally for any returned session (GoTrueClient.js:2068-2070). The email links carry a bare token_hash, and the client uses the default implicit flow with no PKCE verifier, so the token holder can forward the link to someone else.

### Source trace
1. **entrypoint** `apps/web/src/routes/ConfirmEmail.tsx:31` (ConfirmEmail) — token_hash (line 31) and type (line 32, limited to signup/recovery/invite) are read from attacker-suppliable query parameters on the public /auth/confirm route.
1. **propagation** `apps/web/src/routes/ConfirmEmail.tsx:39` (ConfirmEmail useEffect) — verifyEmailLink is called once on mount. The only guards are that the token and type are present and the effect has not already run (line 37). The session from useSession (line 29) is never consulted before verifying.
1. **propagation** `apps/web/src/lib/auth-api.ts:126` (createAuthApi.verifyEmailLink) — Calls client.auth.verifyOtp({ token_hash, type }) directly, with no identity check.
1. **propagation** `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:2069` (GoTrueClient.verifyOtp) — If /verify returns a session with an access_token, _saveSession overwrites the stored session. Line 2070 then emits PASSWORD_RECOVERY or SIGNED_IN. There is no comparison with the existing session and no logout of it.
1. **sink** `apps/web/src/routes/ConfirmEmail.tsx:47` (ConfirmEmail render) — Navigates the victim, now signed in as the token's account, to /reset-password (recovery), /reset-password?welcome=1 (invite), or the attacker-chosen same-site path from next (line 46).

### Verified evidence

## 7. Anonymous sign-up and confirmation-resend calls can use up the project-wide auth email quota, blocking other users' password-reset, confirmation and queue-invite emails

## 8. Unbounded trip-documents uploads leave row-less objects that no authenticated principal can reclaim after trip deletion or leaving
