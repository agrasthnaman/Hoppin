# TripApp Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a shared group-trip planner (itinerary, bookings, documents, expenses, polls, weather, maps) as an offline-capable web app, with a backend and a pure-TypeScript core that a native iOS/Android app can reuse.

**Architecture:** A TypeScript monorepo. `packages/core` holds all domain logic as pure functions (day layout, settlement, sync queue, export summary), so it is unit-tested without a browser and reused later by a native app. `apps/web` is a React PWA that reads and writes through Supabase (Postgres + Auth + Storage). Privacy (private items, personal documents) is enforced by Postgres row-level security, not by the client. The web app keeps a full local copy of the trip in IndexedDB.

**Tech Stack (my call, owner delegated it):** TypeScript (strict); React + Vite + vite-plugin-pwa (Workbox); Tailwind CSS + shadcn/ui + Lucide icons + Motion (animation); Playwright + axe (visual and accessibility QA); Unsplash/Pexels image APIs; Dexie (IndexedDB); TanStack Query; Supabase (Postgres, magic-link Auth, Storage, RLS); Vitest + Testing Library; PGlite (in-process Postgres, for migration and RLS tests, because Docker is blocked by the org's JFrog policy); MapLibre GL with OpenStreetMap tiles; Open-Meteo (weather, no key); Frankfurter (ECB currency rates, no key); pdf-lib (export PDF); Resend (email). Hosting: Cloudflare Pages (web) + hosted Supabase. All swappable behind interfaces defined in core.

**Spec:** `docs/superpowers/specs/2026-11-03-tripapp-design.md`

## Global Constraints

- Web first; mobile later; backend and `packages/core` must not depend on browser APIs.
- Trip size about 10 people; one friend group first, but trips and accounts are separate in the data model.
- Sign-in is passwordless: name + email, emailed link.
- Shared member items go live immediately, with no organizer approval.
- Shared optional items show as small avatar chips (initial + short title) inside the time slot; private items show as a muted dashed line to the owner only.
- Item times are stored with their time zone and are local to the item's location.
- Edits: only an item's creator and the organizer can edit it; the organizer can grant edit rights per person; every change goes to a change history.
- Passports/visas: visible only to the owner and the organizer, cached offline only encrypted, excluded from the immigration export unless that traveller opts in.
- Offline: every screen shows "last synced"; warning after 24 hours; offline edits sync later; a field changed by someone else is last-write-wins with a visible notice to the overwritten person; nothing is dropped silently.
- Offline storage assumption: at most a few hundred MB per trip.
- Expenses stored in the paid currency with the exchange rate captured at entry; settlement computed in one trip base currency; equal split by default, custom amounts allowed; named guests allowed in splits.
- Notifications: in-app plus email; web push where supported; batched over a few minutes.
- Immigration export: PDF with a summary page (stays and tickets per person) then the original documents; also a share link that opens without login, expires, and can be revoked.
- If offline data is lost on iPhones, the native iOS app moves earlier.
- npm installs must go through the org's Artifactory npm registry (`https://entplus.jfrog.io/artifactory/api/npm/npm-virtual/`). Never use the public registry.

## Review Focus

1. A flight that departs on one day and lands the next day in another time zone: it must appear on the right day for each viewer and not twice. (Task 4)
2. A member removed by the organizer: server access ends immediately and the app wipes their local cache on next contact. (Task 3, Task 6)
3. An offline edit to an item that someone else deleted online: the user sees a notice and the edit is kept as a recoverable draft, not dropped. (Task 7)
4. An expense whose split does not divide evenly in cents, or a guest with a zero share: balances must still sum to exactly zero. (Task 10)
5. Export with a traveller who has no documents, or an upload type the PDF merger cannot read (for example HEIC): the export still completes and lists what was skipped. (Task 16)

## Product Scope Summary

Roles: Organizer, Member, Booker (a member who owns a booking). Content types: trip, day, item (flight, stay, activity, transport, plan), document (shared or personal), expense, poll, RSVP, change entry, share link.

### Screen inventory (every screen must work offline from the local cache, except where noted)
| Screen | Who | Purpose |
|---|---|---|
| Sign-in / Join via invite | anyone with a link | Name + email, emailed link; pending-approval state |
| Trips list | member | Trips with hero image, dates, "last synced" |
| Trip home / Today | member | Now and next, stay address, Maps link, weather, quick actions |
| Day view | member | Timeline, group blocks, avatar chips, private dashed lines, day weather, day map toggle |
| Item detail | member | Details, location link, documents, who is interested, "I'm in", edit history |
| Add / edit item | creator, organizer, granted editor | Item form, visibility (just me / everyone), group vs optional |
| Bookings | member | All stays, flights, tickets in one list, filter by person |
| Documents | member | Shared documents; "My documents" for personal ones |
| Money | member | Add expense, split, balances, "who pays whom", home-currency toggle |
| Polls | member | Create, vote, close, add winner to itinerary |
| Members | organizer | Pending approvals, roles, edit-rights grants, remove |
| Export & share | organizer | Immigration PDF, opt-in for passports, share link with expiry and revoke |
| Notifications | member | In-app digests of changes |
| Sync status | member | Last synced, queued edits, conflict notices, stored size |

### Permission matrix (enforced by database row-level security)
| Action | Organizer | Member | Booker | Pending/removed |
|---|---|---|---|---|
| Read shared items, shared documents, polls, expenses | yes | yes | yes | no |
| Read another member's private item | no | no | no | no |
| Read a personal document | owner and organizer only | own only | own only | no |
| Create shared or private item | yes | yes | yes | no |
| Edit or delete an item | any | own items, or if granted | own items | no |
| Approve, remove members, grant edit rights, create share links | yes | no | no | no |

### Offline strategy
- **What is stored:** the trip snapshot (items, bookings, members, expenses, polls, last forecast and rates), shared documents, the viewer's personal documents (encrypted), and the last viewed map list.
- **When it refreshes:** on app open, on regaining connectivity, and on a manual "refresh" button. Realtime updates apply while online.
- **Writes:** queued locally with a base version, flushed when online, reconciled per field (see Task 7).
- **Documents:** downloaded in the background after the first sync, newest trip first, with a progress indicator; a "Make everything available offline" button forces it.
- **Honesty:** every screen shows "last synced" and an offline banner; stale after 24 hours.
- **Risk gate:** iPhone storage eviction is tested in Task 9 before later milestones are treated as done.

### Testing strategy
- Unit tests for all core logic (Vitest). Row-level security tests in PGlite. Component tests with Testing Library.
- End-to-end tests with Playwright: sign in, join, add item, offline reload, sync. Run them in CI once GitHub is set up.
- Visual checks: screenshots at phone and desktop widths for each screen, reviewed by a person (see UI section).
- Accessibility: automated axe checks per screen, plus keyboard and screen-reader pass on the main flows.
- Real-device checks: two iPhones and one Android phone for offline, install, and push.

### Security and privacy
- Personal documents: row-level security plus short-lived signed URLs; encrypted at rest on the device.
- Share links: random unguessable tokens, expiry, revocation, and no personal documents unless opted in.
- No secrets in the client except the public Supabase key; service keys only in server functions.
- Removed member: server access ends at once; the app wipes the local cache on next contact.
- Photo credits and licences are stored with each image (see UI section).

### Risks
| Risk | Mitigation |
|---|---|
| iOS evicts web-app storage | Task 9 gate; native iOS app moves earlier if it happens |
| Free weather/currency/map services change or throttle | Provider interfaces in core; cached results; swap without UI changes |
| Image licence terms (stock photo APIs) | Store credit with every image; follow each API's attribution rules |
| Scope (v1 is large) | Four milestones, each shippable; milestone review before the next |
| Org package policy blocks a dependency | Surface the curation reason; choose an alternative or request a waiver |

## UI and Design Plan

**Goal:** a modern, warm, photo-led, mobile-first interface with tasteful motion, light and dark themes, and accessible contrast. Travel apps feel good when they show places, so each trip and each day leans on imagery.

### Design principles
1. Mobile first: the day view, Today view and documents are used on phones in transit. Large tap targets, one-handed reach, bottom navigation.
2. Calm by default: group blocks are bold, optional chips are small, private lines are muted. Nothing competes with the plan.
3. Photo-led: a hero image per trip, per destination and per stay card.
4. Motion with purpose: transitions explain what changed; nothing blocks the user; honour the reduced-motion setting.
5. Trust cues: "last synced", an offline banner, and visible "just me" markers.

### Design system (Task U1)
Tailwind CSS tokens (colour, spacing, radius, type scale), light and dark themes, one accent colour plus a per-person colour for avatar chips, an icon set (Lucide), and a component base on shadcn/ui (accessible Radix primitives, code lives in our repo). Motion library for animation.
